上行带宽最大化压缩

目标：在小上行带宽（以 10 Mbps 为算例）的家用盒子上，让一台服务器能带更多人。 本页所有数字来自本机工作树实测与线上探测，不是估算值。

首载提速 316× 稳态人均 60 B/s 移出素材 462.6 MiB
1 结论先行 上行不是稳态瓶颈，是首载瓶颈

这是本轮最重要的发现，它决定了后面所有取舍：稳态流量小到不值得压，真正吃满上行的是新玩家第一次进场那一次。

优化前人均上行≈60 B/s467.9 MiB
优化后人均上行≈60 B/s1.48 MiB
10 Mbps 下20,000+ 人（先撞 CPU / fd）从「1 人 6.5 分钟」变「1 人 1.2 秒」
取舍：花力气压 WebSocket 帧收益接近零，花力气把素材和代码挪走收益是几百倍。 本轮 90% 的收益来自「不让盒子发字节」，而不是「把字节压得更小」。

IMPLEMENTATION

落地措施与实测收益

按收益从大到小排列

措施 1 · SP_ASSET_CDN：把素材整块搬出盒子（收益最大）

SP_ASSET_CDN=https://weishucdn.jiangjiangze.icu/

运行时把 data/assets.json 里 7,969 个 /assets/… 引用改写成绝对 CDN URL 再回给客户端。线上核验：该接口实测 1,408,362 字节，全部指向 CDN —— 已生效，无需改动。

收益：盒子出口直接砍掉 462.6 MiB/人，改由 Cloudflare 边缘承担。

⚠️ update\PAUSE_AUTOUPDATE 必须保留：sp_update2 会重写槽脚本并丢掉 SP_ASSET_CDN，素材会静默回落到盒子本地（盒子是无素材版）， 表现为图片全挂 + 上行被打满。

措施 2 · 静态代码 gzip level 6

目录文件原始gzip l6剩余
js1321.89 MiB0.667 MiB35.3%
vendor72.82 MiB0.629 MiB22.3%
css150.33 MiB0.084 MiB25.4%
i18n40.29 MiB0.096 MiB32.7%
合计1585.33 MiB1.475 MiB27.7%
  • GZIP_MIN_BYTES = 512：小文件不压（压完带 header 反而变大，实测 chat 51 B → 94 B 就是反例）。
  • vendor/ 占 54%，且 CF 边缘实测已 HIT —— 这 2.82 MiB 里大部分连盒子都不用出。

措施 3 · ?v=<buildTag>：让复访归零

在回给浏览器的 index.html 上给每一个自有引用追加版本戳 （buildTag = public/index.html + public/js + public/css 的 size+mtime 运行时哈希，与 /healthz.build 同源）， 命中 immutable 一年缓存。

  • 覆盖 25/25 处引用，含 importmap 的 JSON 值。
  • index.html 自己保持 no-cache，所以新版本能立刻生效。
  • 线上实测 max-age=14400 → max-age=31536000, immutable。

收益：复访上行 = 0 字节。

措施 4 · permessage-deflate 窗口 12 → 9

serverMaxWindowBits: 9,          // 512 B（原 12 = 4 KiB）
serverNoContextTakeover: true,   // 保内存上界
clientNoContextTakeover: true,
threshold: 512,                  // 小帧不压
concurrencyLimit: 8,
zlibDeflateOptions: { level: 6, memLevel: 5 }
  • 小窗口用更便宜的距离码，实测反而更省：35.8% vs 36.5%、28.8% vs 30.0%。
  • ⚠️ 默认路径几乎用不到它：clientCombat 默认 on，战斗跑在玩家浏览器里， 服务端只在 AI / 接管 / SP_COMBAT=server 时才发 b.snap。

措施 5 · clientCombat: on（别退回去）

这是天然的最大带宽优化，不是我们做的，但必须守住：战斗逻辑在各端浏览器跑，服务端不广播 30 Hz 快照。

单帧30 Hz 每秒10 Mbps 容纳
未压1,058 B31.0 KiB/s39 人
deflate w9252 B7.6 KiB/s160 人

压完是 4 倍，但只要 clientCombat 退成 off，这两种都比默认路径贵 100 倍以上。 这是本轮唯一有数量级意义的风险点。

措施 6 · 背压与节流（已有）

  • snapDropBytes = 1 << 20：b.snap 是唯一可丢帧， 缓冲超 1 MiB 就跳过 —— 上行被堵时自动降载而不是堆积。
  • heartbeatMs = 30_000：心跳 30 秒一次，双向约 1 B/s，可忽略。

优化前是「一个玩家进来就把上行占死 6 分半，期间所有人都卡」—— 这不是并发数问题，是可用性问题。

表 B · 稳态（决定「能挂多少人」）

场景人均上行人均速率10 Mbps 最大容纳说明
A. 大厅 / 待机≈40 B/s≈320 bps31,250 人 lobby.list gz 161 B / 5 s + 心跳 + 偶发聊天
B. 对局中（默认 clientCombat）≈60 B/s≈480 bps20,833 人 服务端几乎不发 b.snap
C. 对局中（服务端模拟，未压）31,744 B/s254 kbps39 人 SP_COMBAT=server / AI 接管
D. 对局中（服务端模拟，deflate w9）7,782 B/s62 kbps160 人 同上，开启压缩
读法：A / B 的数字大到没有意义 —— 现实中会先撞 CPU、每进程 fd 上限、maxConnections。 也就是说默认配置下上行根本不构成限制，2 万人只用来说明余量有多大。
C → D 的 39 → 160 人是措施 4 的真实价值，但它只在非默认路径上成立。

结论

优化前，10 Mbps 上行的实际容量是 1~2 个新玩家排队进场（素材占死）； 优化后，稳态容量由 CPU 决定（万级），首载吞吐 0.81 人/s 且复访为 0。

已评估但否决的方案

都实测过，不是拍脑袋否的
方案实测结论为何不采用
brotli 静态压缩 再省 295 KiB（1.475 → 1.187 MiB，−19.5%），但压缩耗时 92,138 ms vs 2,083 ms = 44.2× 一次性收益 20%，代价是构建慢 44 倍 + 全站缓存策略改动。已决定保持 gzip l6
上下文接管（context takeover） 实测 4.1% vs 24.6% —— 收益显著 内存上界不可控（每连接保留 LZ77 历史）。内存测量三次结果互相矛盾，本轮不下结论
把 5 MB 代码挂 git 镜像源
（jsDelivr / Statically / ghfast）		 public/vendor/ 在 .gitignore。git ls-files = 0 —— 54% 的载荷根本不在 git 里；且所有 raw 类镜像返回 text/plain + nosniff，ES module 直接被浏览器拒绝 一票否决：源不存在 + MIME 致命
走 CF 隧道承载静态资源 隧道只中继连接，字节仍从盒子网卡出去，上行瓶颈原地不动 不解决目标问题

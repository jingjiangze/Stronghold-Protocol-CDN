落地措施与实测收益

按收益从大到小排列

措施 1~3 贡献了几乎全部收益，4~6 只影响非默认路径或防止回退。 每张卡片第一行的「收益」就是它的全部价值，可以据此决定要不要做。

措施 1 · SP_ASSET_CDN：把素材整块搬出盒子

收益：盒子出口砍掉 462.6 MiB/人，改由 Cloudflare 边缘承担

SP_ASSET_CDN=https://weishucdn.jiangjiangze.icu/
  • 运行时把 data/assets.json 里 7,969 个 /assets/… 引用改写成绝对 CDN URL 再回给客户端。
  • 线上核验：该接口实测 1,408,362 字节，素材条目全部指向 CDN —— 已生效，无需改动。
⚠️ 必须保留 update\PAUSE_AUTOUPDATE：sp_update2 会重写槽脚本并丢掉 SP_ASSET_CDN，素材会静默回落到盒子本地（盒子是无素材版）， 表现为图片全挂 + 上行被打满。这是唯一能让本措施归零的操作。

措施 3 · ?v=<buildTag>：让复访归零

收益：复访上行 = 0 字节（第二次以后不问盒子要任何东西）

  • 在回给浏览器的 index.html 上，给每一个自有引用追加版本戳，命中一年 immutable 缓存。
  • buildTag = index.html + js + css 的 size+mtime 运行时哈希，与 /healthz.build 同源。
  • 覆盖 25/25 处引用，含 importmap 的 JSON 值。
  • index.html 自己保持 no-cache，所以发新版能立刻生效。
  • 线上实测：max-age=14400 → max-age=31536000, immutable。

措施 4 · permessage-deflate 窗口 12 → 9（仅战斗帧口径）

收益：单帧约 4.2×（1,058 → 252 B），但只在非默认路径上成立

serverNoContextTakeover: true,   // 保内存上界
clientNoContextTakeover: true,

  • 小窗口用更便宜的距离码，实测反而更省：35.8% vs 36.5%、28.8% vs 30.0%。
  • ⚠️ 默认路径几乎用不到它：clientCombat 默认 on，战斗跑在玩家浏览器里， 服务端只在 AI / 接管 / SP_COMBAT=server 时才发 b.snap。

总结

优化前，10 Mbps 上行的实际容量是 1~2 个新玩家排队进场（素材占死）； 优化后，首载吞吐 0.81 人/s，复访为 0。

⚠️ 2026-10-12 再修正：稳态容量不是「由 CPU 决定（万级）」，也不是「2,048 → 505 B/s」—— 那两版分别建立在「漏了 m.public 的 60 B/s 建模值」与 「机器人座位（收不到单播）的样本」上。换成人类座位整局逐字节实测后： 稳态人均 57.5 B/s，10 Mbps ≈21,000 人。 ⚠️ 但冷启动（新玩家 5.4 MB，盒子自己发、CF MISS） 摊到 60 分钟是 1,573 B/s —— 它才是现在的天花板。详见下一节。

找到的真 bug：广播路径从来没压过

m.public 走的是广播（Lobby.broadcastRoom → sendRaw）， 而压缩白名单只在 send()（单播）里被查询 —— 广播那条路径从来没传 compress。所以无论白名单怎么写，m.public 永远不会被压缩，白名单对它等于死代码。

修法：broadcastRoom 按 isCompressibleType 传 compress；两条重放路径（pendingResult / runResync）同样压。

两个参数故意不声明（2026-10-12）

选项状态
serverNoContextTakeover不声明＝保留上下文接管（m.private 4.07× → 43.55×）
serverMaxWindowBits不声明＝zlib 默认 15 位（声明了会 400 断连）

⚠️ 写 serverNoContextTakeover: false 是错的 —— 字面 false 是「强制要求」，会拒绝要 no-context-takeover 的客户端（HTTP 400）。旧的 serverMaxWindowBits: 12 同样是潜伏 400 隐患，已去掉。 浏览器 WebSocket 自动解压，对客户端完全透明。

观战 / AI 节流：不是本场球员的观战者每 2 帧才收一次 b.snap，本场球员照收每一帧。 覆盖两类 —— 纯观战者（被淘汰队友、观战席）与 没人打的场（全 AI 场，watcher 全是非球员）。 b.ev 永不丢。它与「链路自适应速率」合成：非球员拿到的是该场当前发射速率的一半。
把 b.start 也压掉（真机 A/B）：人均 125.3 → 57.5 B/s（−54.1%）； 整局逐字节 应用层 70,626 B → 在线 8,610 B（8.20×）；逐帧校验 36 帧 / 解析失败 0。 它不可丢（isDroppable 只认 b.snap） ⇒ 不存在「进了 deflate 上下文却没送达」的 desync 路径。回退 = 写 none 进 update/ws-extra.txt + 重启该槽。

压完之后 m.public 仍是唯一的大头。它的 JSON 高度重复 （players[].bonds 一个字段就占整帧 ~2/3），所以下一步是 delta：

④ 逐收件人 delta（叠在 ③ 上）2.34×

⚠️ 两个前提让这 2.98× 现在等于没上线：① SP_PUB_SYNC 默认 full （delta 默认关）；② ③④ 在 re-apk 分支，而盒子跑 master-play ⇒ 盒子拿不到。
⚠️ 另一条口径警告：这倍数以 m.public 为单位，而整局实测里它只占 3% ⇒ 即便全部兑现，对人均 57.5 B/s 也只有几个百分点的影响。继续在它身上抠，边际收益已经很小 —— 下一轮该做的是冷启动。

再进一步：「客户端本地推演 + 服务端只发事件」会砍掉哪些可见内容

这是 delta 的极端版。它会看得见地砍掉 / 劣化：

  1. 队友的实时棋盘与羁绊 —— 现在由服务端权威下发；事件化后客户端自己回放，任何 RNG / 时序分叉都显示成错的棋盘 / 羁绊 / LP。
  2. 敌人预览与波次 —— 来自服务端 RNG，客户端拿不到种子就复现不出。
  3. Boss 血池 / 团队 LP / 联防计数 —— 共享权威值，本地累加分叉即错。
  4. 隐藏信息 —— 别人的商店 / 手牌服务端故意不发；要推演就得发 → 要么泄露（外挂面），要么推不出来。
  5. 结算结果 m.result —— 服务端判定；事件化让客户端自算 = 可伪造胜负，必须保留服务端权威，砍不掉。
  6. 倒计时 / deadline 与断线重连 —— 现在重连靠重放一份全量 m.public；事件化后要重放整条事件日志，重连成本回来了。

结论：服务端不能放弃对结果 / 伤害的权威（否则就是外挂），所以砍得掉的是队友状态保真度与敌人预览，砍不掉权威层。 能落地的是「服务端发增量 / 事件、客户端维护本地镜像」—— 正是上面的 delta。

ANALYSIS · CONSTANTS OUT OF THE HOT FRAME

把「整场不变的字段」请出热帧

基线 + 客户端合并；重连与兜底都按快照率那套做（PR #157，待合并）

m.public 里有一批开局即定、之后不再变的字段 （lastRound / modeId / difficulty / stageId / factions / disabledBonds / drawnDisabledBonds / bannedChess / bossId / hiddenBossId）。而 permessage-deflate 用的是 serverNoContextTakeover（每帧独立压） —— 帧里任何常量，都要在每一帧付出它的压缩后大小。这就是它们值得搬走的全部理由。

基线 + 合并（重连是重中之重）

  • 热帧变紧凑帧，常量只在基线（full: true）里走一次；
  • start() 在阶段推进之后、flush 之前给每个在线真人席位发一份基线；
  • _resync()（加入 / 重连 / 观战席中途加入）本来就发完整视图；
  • 客户端把 m.public 从整份替换改为合并：见基线就丢弃镜像重来， 否则合并 —— 紧凑帧再也擦不掉常量；
  • 结算屏重放保留完整帧，否则重连后会被重放一帧没有 difficulty 的视图。

兜底（照抄 10Hz↔20Hz 那套）

  • 能力位每 socket声明（hello.pub），每次 hello 重新求值；
  • 未声明的一律发完整帧 —— 老客户端、第三方客户端、部署前打开还在跑旧 JS 的页面， 行为与今天完全一致；
  • hello.version 仍强校验，所以能力位是新增的可选字段，不是版本号；
  • 基线一定先到（start() 与 _resync() 都发）， 对应快照率那条"慢 tick 必须是快 tick 的子集"的守恒。
还没做（按顺序）： ① players[].bonds 按收件人定制（只发"屏幕上"那 1~2 个球员），单独约再省 24% wire； ② delta（只发变化字段），在裁剪之上再约 1.24×（合计 2.05×）； ③ 上游 PR #91 的只读状态接口（给外部观察者，不动对局内广播）。

帧率、传输协议与自适应高刷

起因：「帧率和传输协议有关吗，目前 60 帧体感卡顿，要自适应高刷」。 下面是逐帧仿真与源码核对的结论 —— 与带宽无关，但和同一台服务器上跑的那个客户端有关， 所以放在同一个文档站里。

FRAME RATE vs TRANSPORT

三个「率」，先分清楚

帧率与传输协议基本无关
率由谁决定当前值
渲染帧率本地 rAF + Pixi ticker（app.ticker.maxFPS）被硬钉 60
状态更新率（本地战斗）本地确定性 sim，固定步长 1/30 游戏秒 × 2 倍速60 tick / 真实秒
状态更新率（服务端观战）快照率（含按链路抖动自适应那套）10 Hz，抖动链路 20 Hz

自己打的那一局是本地模拟（clientCombat，默认路径）：战斗在浏览器里跑， ws 只传控制与元数据 —— 帧率和传输协议彻底解耦，延迟里也不含网络往返。
唯一有耦合的是看队友的场（服务端跑、推 b.snap）：状态新鲜度由快照率决定。 但因为客户端有插值器，渲染帧率仍可高于快照率 —— 那是「状态有多新」（延迟），不是帧率。

THE 60 FPS CAP

那个上限不是「少画」，是「画得不匀」

逐帧仿真 Pixi 的算法

Pixi 的 maxFPS 做的不是把这一帧画快一点，而是整帧跳过； 判据里还有一个向零截断： 

set maxFPS(t) { if (t === 0) this._minElapsedMS = 0; else this._minElapsedMS = 1000 / Math.max(minFPS, t); }
update(t) {
  ...
  if (this._minElapsedMS) {
    const n = (t - this._lastFrame) | 0;        // ← 向零截断
    if (n < this._minElapsedMS) return;         // ← 不够就整帧跳过
    this._lastFrame = t - (n % this._minElapsedMS);
  }
  ...渲染...
}

逐帧仿真：相邻两个「真正渲染」帧之间的间隔

屏刷新60 帧上限下的帧间隔判读
60 Hz16.667 ms × 99% / 33.333 ms × 1%周期性掉一帧（可见微顿）
120 Hz16.667 × 98% / 25.000 × 2%周期性晚帧
144 Hz13.889 × 57% / 20.833 × 43%3:2 律动 = 真·抖动
165 Hz18.182 × 83% / 12.121 × 17%抖动
240 Hz16.667 × 96% / 20.833 × 4%周期性晚帧
任意maxFPS = 0（不限）→ 完全均匀间隔 = 屏间隔
两个要点。① 144 Hz 上是最典型的 3:2 —— 一半帧停 2 个刷新、一半停 3 个，等效 48/72 fps 交替， 这不需要「掉帧」就足够让人一眼看出顿。
② 连 60 Hz 屏上也有约 1% 的 33.3 ms 间隔：累计时间差一丝不够阈值（| 0 截断）， 整帧被跳过，之后 % 复位也追不回来。也就是说这个上限对任何刷新率都在制造瑕疵。

顺带推翻一条写在注释里的论证

原注释的理由是「sim 每秒 60 tick，多画的帧只是把同一状态画两遍」。这条不成立： 插值器是按游戏时间插值的，渲染时钟连续推进、在相邻快照之间 lerp； 本地战斗把插值延迟设成 2 个 tick 间隔，余量足够，144 fps 下每个 tick 区间会画出约 2.4 个 不同位置的帧。也专门验过不会退化：本地是每动画帧推快照、而游戏时间只在 tick 时前进， 但插值器会丢弃游戏时间没前进的快照，所以不存在零长度区间。
收益的边界：单位是直线匀速时线性插值本来就精确，多画帧看不出差别； 真正受益的是转向 / 加减速、镜头平移缩放、UI、特效、动画采样。

还有一处也被 60 写死：自适应负载控制器

客户端已有一个「负载等级 0–3」控制器（降粒子、降 LOD、远处单位转低频 impostor），判据就是帧时间， 但阈值是按 60 Hz 的帧预算写死的（frameMs > 19.5 判慢、 < 17.6 判够快，而 60 Hz 的预算正是 16.67 ms）。 上限一提到 120，帧预算变成 8.33 ms，这两个阈值立刻失去意义 —— 一台在 120 Hz 下只能跑 45 fps 的设备刚好卡在「不算慢」那一侧，却已经丢掉了大半刷新。

三件事必须一起做

缺一件都白做
#做什么为什么
A 解除数值上限（上限抬到 120，并按显示器间隔取整数分之一） 仿真实证：只有「不限帧 / 整数分之一」在每种刷新率上都均匀
B 负载控制器改成相对帧预算（frameMs > refreshMs × 1.25 判慢） 19.5 / 17.6 是 60 Hz 的数；不改成相对值，高刷下等于关掉了这个控制器
C 安卓侧申请高刷模式（清单 preferredDisplayModeId / setFrameRate） WebView 的 rAF 跟随窗口刷新率；不申请，很多机器默认 60 Hz，A 与 B 全部白做

为什么不直接设成「测出来的 120/144」：那等于用数值上限去逼近一个本来就是它的东西， 反而会因测量误差与漂移重新引入不匀。正确形式是「每 k 个刷新画一帧」 （maxFPS = refresh / k）：120 Hz 屏 k=1 → 120； 144 Hz 屏 k=2 → 72（而不是 120 那个会抖的 6.944 / 13.889 交替）。

验收判据要用「帧间隔直方图」，不是平均 fps。 平均值会把 3:2 律动藏起来 —— 144 Hz 屏上平均仍然是 60。 合格 = 帧间隔只有一个取值（等于显示器间隔），或退档时恰好是它的整数分之一。
HONEST LIMITS

风险与边界

不是纯赚的改动
  • 不限帧会涨 CPU / GPU 与耗电，弱机上可能更糟 —— 所以必须配 B 的相对阈值与「退回 60」的开关。
  • 收益主要在镜头 / UI / 特效 / 动画采样，不在单位路径（线性插值本来就精确）。别期待「所有东西都变顺」。
  • 安卓不一定给：有些机型或省电模式会把窗口钉回 60。必须先在真机上量出显示器间隔，再谈优化。
  • 2D + 3D 棋盘同时渲染可能才是帧预算的大头；上高刷前值得先量「谁在吃帧时间」。
  • 本页的量化部分全部来自 Pixi 算法的逐帧仿真 + 源码逐行核对，没有真机数据。

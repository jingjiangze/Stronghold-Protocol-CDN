1 APK 端的 mod 梳理 分支 mine/re-apk · 壳轴 shell-v2.9.102 · 上游轴 v0.2.1

壳的思路是「零上游改动」：上游源码逐字节不动，所有内容注入都发生在 ① 构建期装配（extras 覆盖 / patch 重放 / overlay 拷贝）与 ② 运行时拦截（资源解析优先级 + 页面全局通道 globalThis.__SP__）。所以梳理 APK 端，就是梳理四条轴各自能装什么、谁覆盖谁、怎么关、怎么回滚。

1.6 那 APK 端做 mod，能做到哪一步？

能做到：换皮与素材

皮肤轴 + L2 素材轴。这是 APK 唯二「按内容粒度」可装可卸的通道；皮肤连 catalog 都不签名，属于玩家本机自选。

能做到：加服务端能力（非内容）

server/overlay/*.mjs。它是壳自己的插件面，违反 docs/PACKS.md:137-138 的「No third-party code」，也不是 content pack（不经 pack.json / server/packs.js）。现网三条 overlay 都没碰 ctx.server.packs。

有条件能做到：双端同源的代码 mod

/sim/ 是从磁盘直读 server/sim/ 同一目录（static.js:64，只放 .js、私有 nodedata.js）。若用 extras 覆盖链把 hook 写进 server/sim/content/…，浏览器会拿到同一份文件 → 真双端同构。代价：必须进 ALLOWED_OVERRIDES 白名单、破坏「零上游改动」前提，且 check-extras-overlap 会先判红。

做不到：新盟约 / 新装备 / 干员转正

这三条属于数值与数据，APK 侧没有任何按 mod 叠加数据的路径（slim 只能整树换上游发布）。唯一正解是服务器端 data 包，见板块 2。

2.5 原设计的五个问题，逐条按代码复核

上一轮审计给出的五条「致命缺陷」，方向对，但两条证据错了。逐条重判（图上写什么 → 代码里是什么 → 怎么改）：

缺陷一 · 全局挂载 + 手动回滚 FAIL

判定成立，但根因不是并发写内存，而是与官方语义冲突。data 类型被规范钉在 live:false（进程生命周期内固定）。 两条合法解法：(A) 启动时确定启用哪些包（进程级；多房间天然一致，代价 = 要重启 host 才换配置）； (B) 房间级派生视图 Object.create(officialGd)（房间销毁由 GC 回收，不需要「卸载 / 恢复官方数据」这段脆弱逻辑）。 选 (B) 就必须承认它不是官方 packs 的 data 语义，而是自己的派生视图层；别在文档里把它叫「pack 热重载」。 现网风险确实存在：单进程多房间，原地覆写会让别的房间刷出 mod 装备。

缺陷二 · 双端确定性 改述

原述「只在服务端跑 custom.js 会 Desync」不准确。真实默认是客户端算战斗（clientCombat 默认 on）， 服务端做的是结果校验 + 必要时重算（validateClientResult，network.md:86：结构白名单 + 合理性上下界，例如 每盟约 layerGains ≤ min(60 + 4·round, 999 − 起始层)、盟约必须存在且被玩家快照点名、coins ≤ Σ bounty）。 所以后果是：客户端不懂这个盟约 → 报不出这个层数 → 服务端判结果可疑并自己重算 → 玩家看到的画面与实际结算不一致，而不是「双端各自算歪」。 规范里那句「a battle must run the same data on the server and in every browser」就是解药：纯数据天然满足；代码 hook 天然不满足。

缺陷三 · 商店偏置归属 PASS

完全成立。SharedPool.rollItem(rng, maxTier)（pool.js:148-168）连「是谁在刷新」都不知道， 档位概率还跟随棋子池剩余拷贝（tierShares），只做纯随机 + 向低档 / 高档回退。 玩家级落点是 economy.js:69-72。 而 giveBondBiasOnly 与 shopBondOrder 三个分支全 0 命中 —— 要它就得新增字段并同时改 pieceBonds 与 sim 侧读取。

缺陷四 · 自选清洗与联机同步 PASS（细节纠正）

结论对：不该外挂 stripPackOperators()，数据驱动就够。纠正三处： ① checkDiyPicks 在 shared/protocol.js:237（宽松语义：逐槽累加、冲突时前槽胜出、返回 dropped 计数）， shared/diy.js 里只有单数 checkDiyPick(:156) 与严格的 validateDiyPicks(:249)； ② 数据源是 data/backups.json 的 diy 键，没有 data/diy.json； ③ 同步广播是 room.state，不是 room.update。另外：任何玩家都能发 room.diy（没有房主门），旁观者被排除。

缺陷五 · 分支断层 已纠正

原述「py 分支完全没有 packs 代码」只对一半：shared/packs.js 在 py 分支上存在且与官方逐字节相同（悬空：它注释引用的 server/packs.js 与 docs/PACKS.md 都没有）。 缺的是 server/packs.js、packs/、tools/packs.mjs、/packs 路由、docs/PACKS.md。详见板块 4。

新增缺陷六 · 原审计漏了一条：结果校验白名单 需实测

服务端会把玩家上报的战斗结果按白名单重建（泄漏归属、层数上界、金币上界、单位状态只允许自己的 board uid）。 mod 若新增会大量叠层的盟约或新敌人，可能撞到静态上界而被判可疑 → 触发重算路径。 这条必须在 mod 管理器的验收里跑，而不是等玩家上报。

3.1 两个方案怎么选

维度A · 双端同构（数据包）B · 纯服务端权威
与官方规范直接对应 data 类型与「同数据双端跑」合规，但需要 SP_COMBAT=server 关掉默认路径

素材 CDN

把上游（sganggs/Stronghold-Protocol） 的静态素材镜像到边缘，让部署机不再承担几百 MB 的重复流量。内容就是上游 Release 完整包里的同一批文件， 逐文件校验过，不做任何转码。

1 玩家：两种下载，按你的情况选一个 不写代码 · 解压即用 · 随时撤销

两条路都能让素材改从 CDN 走、把几百 MB 从你的上行带宽上拿掉。 区别只在于你手上有没有一份能跑的游戏服——有就选 A，没有就选 B。

A · 你已经有能跑的游戏服
下载侧车包 镜像加速下载
stronghold-cdn-dropin-v0.2.2.zip · 正在读取最新版本…
十几天 KB。内含启动脚本（Windows / Linux）、侧车代理、验收脚本、说明与排错表。 它不会改动你部署包里的任何文件，删掉文件夹就完全回到原样。
B · 你还没有游戏服，想直接开一个
下载整合包 镜像加速下载
stronghold-official-cdn-v0.2.2.zip · 正在读取最新版本…
二十几 MB 的官方最新包，不含素材，只把素材地址改成了本 CDN， 其余（代码、数据、依赖、启动脚本）与官方包完全一致。依赖已打包，不需要 npm install： 解压后 node server/index.js 就能跑。 首次进游戏时素材按需从 CDN 拉取，所以它不占你任何上行带宽。
两个包会跟着上游最新版滚动更新——上面的链接永远指向最新那份，不用记版本号。 上游发新版后，A 只需重下一次（十几 KB），B 请重新下整包，不要用官方的 update 增量包升级 （那会把你带回需要本地素材的状态）。
  1. 1
    下载并解压到部署目录旁边
    解压后得到一个 stronghold-cdn/ 文件夹。放三种位置都行：放进部署目录里面、 放在它旁边、或放在它上一级——启动脚本会自己找到部署目录。部署目录被改过名（例如 servers/）时， 启动前设一下 SP_DEPLOY_DIR=部署目录。
  2. 2
    双击启动
    Windows 双击 stronghold-cdn\start-with-cdn.cmd； Linux / macOS 运行 sh stronghold-cdn/start-with-cdn.sh。 它会把游戏服起在内部端口，在外层代理，并把三张素材清单在响应里改成 CDN 地址。房间与对局的 WebSocket 原样透传。
  3. 3
    验收：跑一条命令
    另开一个终端：node stronghold-cdn/verify-cdn.mjs http://127.0.0.1:3000
    看到 OK: art is served from the CDN 就成了（要求清单里 0 条素材仍指向本机）。

撤销 / 回退

删掉 stronghold-cdn/ 文件夹，按原来的方式启动即可。部署包自始至终没有被修改过。

它做了什么 / 不做什么

  • 做：把三张清单里的 /assets/…、/fonts/… 改写成 CDN 绝对地址
  • 不做：不碰部署包里的文件、不动存档、不改游戏数据
  • 需要：Node.js 18+（游戏服本来就要）
遇到的情况怎么处理
素材还是本机在发你连的是内部端口或另一个实例；请走启动脚本打印的那个端口
找不到部署目录启动脚本会告诉你三种摆放位置；或显式设 SP_DEPLOY_DIR
页面白块 / 控制台报 CORSCDN 响应缺 Access-Control-Allow-Origin；把浏览器控制台的报错发出来
端口被占用PORT=8080 再启动（内部端口自动跟着变）
验收报缺文件用 /cdn/v1/index.json 对账；缺什么补什么，清单是唯一真源
2 Agent：对所有服务器通用 读契约 · 按拓扑套做法 · 跑验收

不管目标是一份未修改的上游包、本项目的 fork、静态托管、nginx 反代还是 Docker，只有一条规则要遵守： 客户端取素材的唯一来源是清单（data/assets.json、local-assets.json、emotes.json）， 所以把这三张清单里 /assets/… 与 /fonts/… 的 URL 改写成 CDN 绝对地址即可， 不需要改客户端，也不需要改服务器代码。

四条硬约束

  • 只在响应层改写：服务器自己也要读这些清单做完整性校验，改磁盘文件会破坏更新与自检
  • 素材必须带 CORS：客户端用 img.crossOrigin='anonymous'，否则 WebGL 贴图被污染
  • URL 要带版本令牌：?v=<令牌>，否则改版后边缘缓存会继续发旧字节
  • 路径不要自己拼：清单里的地址已经是绝对 URL，照用

先确认目标长什么样

  • 找到部署目录：含 package.json 与 server/（或等价的服务入口）
  • 确认服务端口：GET /data/assets.json 能返回 JSON
  • 记下改写前的一个样本 URL，验收时对照
目标拓扑做法
任何 HTTP 服务（通用） 侧车代理：把服务起在内部端口，在外层代理，只改写三张清单的响应。下载 A（侧车包）用的就是这个，stronghold-cdn/cdn-serve.mjs 可直接抄（含 WebSocket 透传与 accept-encoding 处理）。下载 B（整合包）不用它：清单已经在包里被改成绝对 CDN 地址，服务端不需要任何改动。
本项目 fork 不需要代理，设环境变量即可：SP_ASSET_CDN=https://weishucdn.jiangjiangze.icu/（服务端 server/http/static.js 会改写三张清单；该值启动时读一次，改完要重启）。注意：这个开关是本项目 fork 加的，上游官方包没有——上游的 -lite.zip 里 grep 不到它，所以下载 B 走的是改清单而不是设变量。
nginx 反代 
location = /data/assets.json {
  proxy_pass http://127.0.0.1:3001;
  proxy_set_header Accept-Encoding "";   # 必须：否则拿到的是 gzip，替换不生效
  sub_filter '"/assets/'  '"https://weishucdn.jiangjiangze.icu/assets/';
  sub_filter '"/fonts/'   '"https://weishucdn.jiangjiangze.icu/fonts/';
  sub_filter_once off;
}
三张清单各写一条 location（assets / local-assets / emotes）。
静态托管（无服务端逻辑） 直接取 CDN 上的 /data/assets.json 覆盖本地的同名文件（它已经是绝对地址）。仅当没有服务端会读该文件做校验时才可这么做。
Docker 在容器里跑侧车（把服务入口改成 node cdn-serve.mjs），或按 fork 那条设 -e SP_ASSET_CDN=…。

验收（任何拓扑都跑同一套）

  1. 清单里 0 条素材仍指向本机：node verify-cdn.mjs http://127.0.0.1:<端口> 应输出 OK
  2. 抽样 20 条 CDN URL 全部 200（同一脚本会做）
  3. 浏览器冷启动：控制台 0 报错、棋盘贴图与干员立绘正常、房间能进能打
  4. 回退演练一次：停掉侧车（或去掉环境变量）后按原方式启动，页面仍正常

还有哪些免费 CDN

都要求能绑定自有域名才算"中转"

一个前提：多数免费 CDN 不支持绑定自有域名（jsDelivr、Statically、各种 gh 镜像都只能用它给你的地址）， 想让流量走自己的域名，只能自己加一层反代——那样瓶颈就变成你自己的机器，反而更慢。所以下表按"能不能绑域名"筛过。 国内厂商另有硬门槛：域名要 ICP 备案才能用国内节点加速，本域未备案，所以国内 CDN 目前不可用。

来源免费绑自有域名国内可用结论
Cloudflare R2 + 自定义域是（出口免费）是一般（港/新/日节点）已接入 · 主源
Cloudflare Pages是是同上已接入 · 次源
Cloudflare 抗 DDoS是且不限量随域名生效—已生效（"高防"这层免费档已覆盖）
GitHub Release + 镜像前缀是否镜像可用已接入 · 打包通道
AWS CloudFront12 个月 1 TB/月，之后按量是（ACM 证书）一般待接入：凭据可用，但 agent-cli-minimal 策略**显式拒绝** cloudfront:* 与 acm:*，需要放宽策略或在控制台建
阿里云 / 腾讯云 CDN、又拍云、七牛有免费额度是好需 ICP 备案；本域未备案 → 暂不可用
Bunny CDN否（14 天试用）是较好收费，约 $0.01/GB
Oracle Cloud Always Free是（含 10 TB/月出口）是（自建 nginx 镜像）视机房可行，但要自己开机器与运维
jsDelivr / Statically是否差不建议
Vercel / Netlify 免费档是是基本不可用不建议
接入新来源不需要改代码：在仓库的 origins.json 的 extraOrigins 里加一条 { id, kind, root }， 下一次同步就会把它写进 art.json / mirrors.json， 本页的镜像列表与测速也会自动带上它。

上行带宽最大化压缩

小上行带宽盒子的实测优化与容量表

如果你的部署机上行很小（家用宽带、4G 路由、小水管 VPS），这一份是为你写的。核心结论是反直觉的： 上行不是稳态瓶颈，是首载瓶颈 —— 稳态人均只要约 60 B/s，而优化前一个新玩家进场要吃掉 467.9 MiB， 在 10 Mbps 上等于占死 6.5 分钟。所以收益几乎全部来自「让盒子不发字节」，而不是「把字节压得更小」。

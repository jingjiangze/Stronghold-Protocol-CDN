# 审计：帧率 vs 传输协议 + 自适应高刷方案

日期：2026-10-09 · 对象：`public/js/render/app.js`、`public/js/render/app/host.js`、`public/js/battle/runner.js`、
`public/js/render/interp.js`、`android/`（`re-apk` 分支）
用户原话：**"帧率和传输协议有关吗，我需要做自适应高刷，目前60帧体感卡顿，审计方案"**

---

## 一、结论先行

1. **帧率与传输协议基本无关。** 渲染帧率由本地 rAF + Pixi ticker 决定；传输协议只决定"状态有多新/多密"。
   默认的 `clientCombat` 下战斗**在本地跑**，ws 只传控制与元数据 —— 两者彻底解耦。
2. **"60 帧体感卡顿"有一个与显示器无关的解释：那个 60 的数值上限本身在制造不均匀帧间隔。**
   逐帧仿真 Pixi 的 `maxFPS` 算法：144 Hz 屏上帧间隔一半 13.9 ms、一半 20.8 ms（3:2 律动）；
   **连 60 Hz 屏都有约 1% 的帧被拉成 33.3 ms**。**不限帧在每种刷新率上都是均匀的。**
3. 所以"自适应高刷"不是"把 60 改成 0"这么简单，它有三个必须一起做的部分：
   **解除数值上限**（否则高刷屏也上不去）、**把负载控制器从绝对阈值改成相对帧预算**（否则它会失去意义）、
   **安卓侧申请高刷模式**（否则窗口是 60 Hz，网页端解除也没用）。

---

## 二、三个"率"，先分清楚（回答问题一）

| 率 | 由谁决定 | 当前值 |
|---|---|---|
| **渲染帧率** | 本地 rAF + Pixi ticker（`app.ticker.maxFPS`） | 被**硬钉 60** |
| **状态更新率（本地战斗）** | 本地确定性 sim，固定步长 `1/30` 游戏秒 × 2 倍速 | **60 tick/真实秒** |
| **状态更新率（服务端观战）** | `SNAPSHOT_EVERY` + 本轮新增的按链路自适应 | 10 Hz，抖动链路 20 Hz |

`public/js/battle/runner.js` 头部写得很明确：本地战斗用共享的确定性 sim，**固定 1/30 s tick**，
每动画帧按同样的 wire 格式（`b.snap` / `b.ev`）喂给渲染器。所以：

- **自己打的那一局**：完全本地模拟 → **帧率与传输协议无关**，延迟也不含网络往返。
- **看队友的场**（服务端跑、推快照）：状态新鲜度由快照率决定（10/20 Hz），
  但因为客户端有插值器，**渲染帧率仍可高于快照率** —— 两件事，别混。
- 唯一真正的耦合是：**观战场的"状态有多新"受传输与快照率约束**，而那是延迟问题，不是帧率问题。

## 三、60 帧上限到底做了什么（回答问题二）

### 3.1 Pixi 的实现（从 `public/vendor/pixi.min.js` 逐字反读）

```js
set maxFPS(t) { if (t === 0) this._minElapsedMS = 0; else this._minElapsedMS = 1000 / Math.max(minFPS, t); }
update(t) {
  ...
  if (this._minElapsedMS) {
    const n = (t - this._lastFrame) | 0;        // ← 向零截断
    if (n < this._minElapsedMS) return;         // ← 不够就整帧跳过
    this._lastFrame = t - (n % this._minElapsedMS);
  }
  ...渲染...
}
```

两个要害：**整帧跳过**（不是把这一帧画快一点）与 **`| 0` 截断**。

### 3.2 逐帧仿真结果（`probe-pixi-pacing.mjs`，严格照上面的算法）

统计"相邻两个**真正渲染**帧之间的间隔"（10 秒窗口）：

| 屏刷新 | 60 帧上限下的帧间隔 | 判读 |
|---|---|---|
| 60 Hz | 16.667 ms × 99% / **33.333 ms × 1%** | 周期性掉一帧（可见微顿） |
| 120 Hz | 16.667 × 98% / **25.000 × 2%** | 周期性晚帧 |
| **144 Hz** | **13.889 × 57% / 20.833 × 43%** | **3:2 律动 = 真·抖动** |
| 165 Hz | 18.182 × 83% / 12.121 × 17% | 抖动 |
| 240 Hz | 16.667 × 96% / 20.833 × 4% | 周期性晚帧 |
| 任意 | `maxFPS = 0`（不限） | **完全均匀（间隔 = 屏间隔）** |

两个必须点出来的事实：

- **144 Hz 上是最典型的 3:2**：一半帧停留 2 个刷新、一半停留 3 个，等效 48/72 fps 交替。
  这不需要"掉帧"就足够让人一眼看出顿 —— 这就是"体感卡顿"最可能的来源。
- **60 Hz 屏上也有 1% 的 33.3 ms 间隔**：累计时间差一丝不够阈值（`| 0` 截断），整帧被跳过，
  之后 `%` 复位也追不回来。也就是说**这个上限对任何刷新率都在制造瑕疵**。

### 3.3 顺带推翻一条写在注释里的论证

`app.js:202` 与 `test/render/frame-cap.test.js` 的理由是"sim 每秒 60 tick，多画的帧只是把同一状态画两遍"。
**这条不成立**：`render/interp.js` 是按**游戏时间**插值的，渲染时钟 `renderT` 连续推进、
在相邻快照之间 lerp；`setLocalFeed` 把 `delay` 设成 0.034 s（= 2 个 tick 间隔），余量足够。
144 fps 下每个 16.67 ms 区间会画出 ~2.4 个**不同位置**的帧。

我还专门验过会不会退化：本地是**每动画帧**推快照、而游戏时间只在 tick 时前进，那高刷下会不会堆一堆
"游戏时间相同"的快照？查 `interp.push()`：**游戏时间没前进就丢弃**（`else if (s.t <= newest) return false`），
所以缓冲里每个 tick 只有一条，不存在零长度区间。

**收益的边界（诚实）**：单位是直线匀速时线性插值本来就精确，多画帧看不出差别；真正受益的是
**转向/加减速、镜头平移缩放、UI、特效、动画采样**。"提帧率没用"是错的，"提帧率万能"也是错的。

### 3.4 还有一处也被 60 写死：自适应负载控制器

`app.js` 已有 load level 0–3（降粒子、降 LOD、远处单位转低频 impostor），**判据就是帧时间**：

```js
let frameMs = 16, fps = 60;                       // ← 初始化即假设 60 Hz
if (frameMs > 19.5 && busy) { slowFor += dtRaw; }  // ← 19.5 ms = 60 Hz 帧预算
else if (frameMs < 17.6) { fastFor += dtRaw; }     // ← 17.6 ms
```

**19.5 / 17.6 ms 就是 60 Hz 的预算（16.67 ms）。** 上限一提到 144，帧预算变成 6.94 ms，
这两个阈值立刻失去意义：一台在 144 Hz 下只能跑 45 fps（22 ms）的设备，刚好卡在"不算慢"那一侧，
**却已经丢掉了 2/3 的刷新**。所以自适应高刷必须连它一起改。

## 四、方案

### 4.1 三件事一起做（缺一不可）

| # | 做什么 | 为什么 |
|---|---|---|
| **A** | **解除数值上限**：`app.ticker.maxFPS = 0`（交给 rAF 按显示器节拍走） | 仿真实证：只有不限帧在**每种**刷新率上都均匀 |
| **B** | **负载控制器改成相对帧预算**：`frameMs > refreshMs * 1.25` 判慢、`< refreshMs * 1.1` 判够快 | 19.5/17.6 是 60 Hz 的数；不改成相对值，高刷下等于关掉了这个控制器 |
| **C** | **安卓侧申请高刷模式**（`re-apk` 分支的 `MainActivity`） | WebView 的 rAF 跟随**窗口**刷新率；不申请，很多机器默认 60 Hz，A 与 B 全部白做 |

### 4.2 具体设计

**① 测显示器帧间隔 `refreshMs`**
浏览器没有 API 能直接问刷新率，只能量：rAF 回调间隔的**下界**就是显示器间隔。
做法：滑动窗口取低分位（如 p10）或最小值，并对"设备一直在忙"的情况加保护（p10 比 min 稳）。
**必须周期性重测** —— 安卓会因为省电/温度动态改刷新率。

**② 目标帧率**
`maxFPS = 0`。不推荐"设成测出来的 120/144"：那等于用数值上限去逼近一个本来就是它的东西，
反而会因为测量误差与漂移重新引入不匀（仿真里 `maxFPS=120` 在 144 Hz 屏上得到 6.944/13.889 交替，
仍然是抖的）。

**③ 降载的第二杠杆（可选，但推荐）**
现有控制器降的是"工作量"（粒子/LOD/impostor）。若降到头还是跟不上，再降**帧率目标**——
但**只允许降到显示器间隔的整数分之一**（144 → 72 → 48 → 36），
因为仿真已经证明非整数倍的上限必然产生不匀。这条是"保均匀"与"保性能"之间的正确折中。

**④ 与现有质量设置的关系**
`settings.quality`（高/中/低）继续管画质；新增一个**帧率**项：`自动（默认）` / `60` / `跟随屏幕`。
默认 `自动` = A + B + ③。`60` 保留给"想省电/想要稳定 60"的人（注意：**选 60 就会重新引入
第三节那 1% 的 33.3 ms 瑕疵**，这点要在设置项里说清，或者干脆实现成"60 时锁到 60 Hz 的整数倍节拍"）。

**⑤ 安卓侧怎么申请**
`MainActivity` 里遍历 `display.getSupportedModes()`，挑刷新率最高的模式，设
`window.getAttributes().preferredDisplayModeId = mode.modeId`（API 23+）；
API 30+ 再补 `window.setFrameRate(0, FRAME_RATE_COMPATIBILITY_DEFAULT)` 让系统按内容匹配。
**代价是耗电**，所以建议与 ④ 的"自动"联动（用户选 60 就别申请最高模式）。

### 4.3 落地位置（预估）

| 文件 | 改动 |
|---|---|
| `public/js/render/app/host.js` | `RENDER_MAX_FPS` 从常量变成"策略默认值"（或删掉，改由策略给） |
| `public/js/render/app.js` | `app.ticker.maxFPS` 改为按策略设；`adaptLoad` 阈值改成相对 `refreshMs`；`frameMs/fps` 初始化改为动态 |
| `public/js/render/frameRate.js`（新） | 纯逻辑：测刷新率、策略（自动/60/跟随）、只允许整数分之一的降档 —— **可单测** |
| `public/js/ui/settings.js` | 新增"帧率"项（照 `QUALITY` 的写法） |
| `test/render/frame-cap.test.js` | **必须重写**（它把 60 钉死了，是好事，说明这个改动不会静默发生） |
| `android/.../MainActivity.java`（`re-apk`） | 申请最高刷新率模式，与设置联动 |

### 4.4 验收怎么做

现成的工具就够，不用新造：

- `public/dev/frame-stats.js` 的 `frameFigures(deltas, stutterMs)` 已经能出
  `fps / p50 / p95 / p99 / over33%`；渲染器也已对外暴露 `st.fps` / `st.frameMs`（`public/dev/render-demo.js`）。
- **判据要用"帧间隔直方图"，不是平均 fps**：平均值会把 3:2 律动藏起来（144 Hz 上平均仍是 60）。
  验收标准 = 帧间隔只有**一个**取值（= 显示器间隔），或退档时恰好是它的整数分之一。
- 建议加一个 `refreshMs` 到 stats，并在 perf 页显示 `frameMs / refreshMs` 的比值。

## 五、风险与诚实边界

1. **不限帧会涨 CPU/GPU 与耗电**，弱机上可能更糟。所以必须配 ③ 的降档与 B 的相对阈值，
   并且"自动"要能退回 60。这不是纯赚的改动。
2. **收益主要在镜头/UI/特效/动画采样**，不在单位路径（线性插值本来就精确）。别期待"所有东西都变顺"。
3. **安卓不一定给**：有些机型/系统会限制 WebView 的 rAF，或者省电模式把窗口钉回 60。
   **必须在真机上先量 `refreshMs` 再谈优化** —— 这是第一步，不是最后一步。
4. **2D + 3D 棋盘同时渲染**（stats 里有 `board3d`）可能才是真正的帧预算大头；
   上高刷前值得先用 perf 页量一遍"谁在吃帧时间"，否则可能是在优化错的地方。
5. 我**没有**在真机上测过；本审计的量化部分全部来自
   ① Pixi 算法的逐帧仿真、② 源码逐行核对。真机数据需要你在目标设备上跑一次 perf 页。

**与上面 §4.2 的一处出入（以执行为准）**：§4.2② 当时推荐 `maxFPS = 0`（不限帧），而用户定的上限是 120。
实现取了两者的交集：**上限 120，但在上限之下按显示器间隔取整数分之一** ——
既守住 120 的天花板，又保证帧间隔永远是显示器间隔的整数倍（这才是"均匀"的充要条件）。
所以 144 Hz 屏上得到 72 而不是 120；这正是 §4.2 里"只允许整数分之一"那条。

## 七、剩下的（C）与验收

**C（安卓申请高刷）待你拍板** —— 它是另一条产品线（`re-apk`），改动是 `MainActivity` 里按
`display.getSupportedModes()` 挑刷新率最高的模式设 `preferredDisplayModeId`（API 23+），
API 30+ 再补 `window.setFrameRate(0, FRAME_RATE_COMPATIBILITY_DEFAULT)`。
**代价是耗电**，建议与"上限 60"的开关联动。没有它，A+B 在高刷机上可能一帧都不多。

**验收怎么跑**（现在就能跑，不需要真机以外的条件）：

1. 打开 `/dev/battle-perf.html`（本机或手机浏览器都行），看**实时**的
   「显示器间隔 ≈ N Hz · 上限 M」——这一步直接回答"我这块屏到底多少 Hz"。
2. 点「开始测量（10 秒）」，看结果里的**帧间隔分布**：
   - 只有一个桶（如 `1×100%`）→ **均匀，不抖**；
   - 出现第二个桶（如 `2×57% / 3×43%`）→ **不匀 = 抖**，把这份报告贴回来我按数据调。
3. 复制的报告里已经含显示器间隔、渲染上限、分布、P50/P95/P99、GPU 与设备信息 —— 一次跑完就够。

**判据提醒**：别看平均帧率。稳定 60 fps 与 144 Hz 上的 3:2 律动，平均帧率**完全一样**，
只有帧间隔分布能分开 —— 这也是为什么先做直方图、而不是先调数字。

**诚实的边界**：A+B 会让 CPU/GPU 与耗电上升，弱机上可能更糟（所以配了相对阈值的负载控制器，
以及上限本身）。全部结论来自算法仿真与源码核对，**没有真机数据** —— 所以第 1 步是量，不是改。

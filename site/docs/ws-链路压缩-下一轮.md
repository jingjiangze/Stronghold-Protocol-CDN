## 〇、实测：各种做法**叠加在压缩之上**各值多少

⚠️ 关键口径：deflate 已经在吃重复，所以「裁剪 / delta」**不能与压缩简单相乘**。下表是同批 131 帧实测：

| 方案 | 场总量 | 相对"已上线的压缩" |
|---|---|---|
| 0. 未压 | 589.8 KiB | 4.94× 更差 |
| 1. **完整帧 + deflate（今天线上）** | **119.5 KiB** | — |
| 2. delta + deflate | 74.8 KiB | **1.60×** |
| 3. 裁剪 + deflate | 72.5 KiB | **1.65×** |
| 4. **裁剪 + delta + deflate** | **58.3 KiB** | **2.05×** |

每席位每场 **29.9 → 14.6 KiB**；按 300 s 一场 = **102 → 50 B/s**。
→ 10 Mbps 从 ~2,475 人抬到 **~5,000 人**。（注：`m.public` 已由 PR #157 做掉"整场常量"那一半，即上表"裁剪"的一部分。）

## 一、步骤 ③ — `players[].bonds` 按收件人定制（≈24% wire）

**为什么**：`players[].bonds` 一个字段占整帧的 ~2/3（4 人合计 321.1 KiB/场），而**客户端只显示"屏幕上那一个玩家"**
（`public/js/ui/watchBonds.js`：strip 跟随屏幕上的玩家）。只发 1 人时 bonds 降到 89.8 KiB —— **72% 的羁绊字节
发给了看不见的人**。

**必须做成「按收件人定制」，不能做成「按需拉取」**：
`watchBonds.js` 头部写明「a detail card's bond chips follow the **UNIT's owner** instead（共享战场会同时显示两边的单位）」——
所以**联防 / 最终攻势的共享场需要 2 人**的羁绊。若改成"羁绊按需拉取"，玩家点开队友/单位卡时会出现**空/旧羁绊条**
（可见影响）。按收件人定制则**逐帧推送、零往返、零可见影响**。

- **做法**：服务端为每个收件人保留"屏幕上那 1~2 个球员"（普通场 1 人 = 自己；共享场 2 人 = 双方）的 `bonds`，
  其余剥掉；仍逐帧推送。线上按 `watchers` / `watchPref`（`g.watch` 已带 `playerId`）判"屏幕上是谁"。
- **代价**：放弃 `broadcastRoom` 的"编码一次发多人"（4 席 = 4 次 `stringify`，0.76 帧/s，CPU 可忽略）。
  且**需要一个新的按需通道** `g.bonds → m.bonds`，供"点开一个**当前不在屏幕上**的玩家的羁绊弹窗"用
  （可以先用手上数据乐观渲染）。
- **准入**：`m.bonds` 是**新增消息**（`shared/protocol.js` 的 S2C/C2S 各加一条），客户端只对声明了能力位的连接发。
- **影响面**：strip / 单位卡芯片 / 正在看的弹窗 → 都有数据；只有"点开非屏幕玩家"走一次按需往返。
- **验收**：`bonds` 在热帧里只剩 1~2 人（脚本断言）；共享场打开两个单位卡，两侧羁绊均正确；点开第三个玩家出现
  一次 `g.bonds` 且结局正确。
- **退路**：能力位不声明 → 发全部 4 人（今天行为）。

## 二、步骤 ④ — delta（只发变化字段）

**为什么**：即使裁完，`m.public` 仍是唯一的大头；delta 在裁剪之上再 **1.24×**（合计 2.05×）。

- **做法**：热帧只带**与上一份不同的顶层字段**；`players[]` 逐人 diff。客户端已在本轮改为**合并**（PR #157），
  天然就是 delta 的落地形态；再加 `players[]` 的逐人合并即可。
- **准入**：① 客户端合并（**已在 PR #157 完成**）；② 被清空的字段必须**显式 `null`**，不能"省略键"。
  ⚠️ 现状里 `econ` / `revival` 是**省略**的（`...(econ ? { econ } : {})`）→ 合并会保留陈旧值。**必须先改成显式 null**
  （客户端只用真值判断、没有键存在性检查，已核实）。
- **守恒**：加一条"**周期性全量锚点**"（每 N 帧或每 30 s 必发一次完整帧），对应快照率那条"慢 tick 必须是快 tick 的子集"——
  任何丢帧 / 错序都在有限时间内自愈。
- **影响面**：所有读 `pub.X` 的客户端代码（消费点清单见《当前》§五）—— 因为客户端是**合并**语义，读法不变。
- **验收**：热帧字节降到 ~50 B/s/人；跑一遍重连 / 掉线 / 换人，镜像不残留旧值（关键用例：某字段先有值后清空）。
- **退路**：一个开关 `SP_PUB_SYNC=full|delta`（默认 `full`），一键回全量。

## 三、步骤 ⑤ — 上游 PR #91 的只读状态接口（那 9%）

**为什么**：这一块只有 **9.5%（64.6 MiB / 5 天）**，但量堆起来一样压上行，且它是**能力**不只是省字节。

- **是什么**：上游 **PR #91「按房间码查询只读实时状态接口」**（`GET /api/rooms/{code}/status`，open，by Misyra）——
  给**外部展示工具**用：不登录、不建会话、不占玩家席位，字段白名单过滤玩家 ID / token / 商店。文件：
  `server/roomStatus.js` + 4 项测试（移植成本低）。**它不改变对局内的 `m.public` 广播**。
- **注意**：**「拉取」对玩家侧不省** —— 同等新鲜度下 pull 成本 = N × 轮询率 ≥ push 的 N × 变化率。
  pull 只在**接收方不需要新鲜度**时省（后台标签页、外部工具）。所以这条只对**观察者**做，不要动对局内广播。
- **我们这套部署的现状**：大厅是 HTTP 板 API（`GET/POST/PATCH/DELETE /api/rooms` + DO），数据来自客户端 60 s 自报 +
  聚合其他社区板 —— **观察者本来就不持会话**，所以这条的实际收益主要来自"第三方工具不再需要挂会话"。
- **验收**：`GET /api/rooms/<code>/status` 返回只读 JSON；`HEAD` 支持；不带 token 也能查；
  玩家 ID / token / 商店字段被过滤；限流生效。
- **退路**：纯新增端点，删掉即可。

## 四、顺序与准入（不要跳）

| 顺序 | 事项 | 准入条件 | 单项收益 |
|---|---|---|---|
| ① | 客户端合并 + 基线（**已完成，PR #157**） | — | 0（但是 ②③ 的门） |
| ② | 显式 `null`（`econ` / `revival`） | ① | 0（但是 delta 的门） |
| ③ | `bonds` 按收件人定制 + `g.bonds` 按需 | ① | ≈24% wire |
| ④ | delta + 周期性全量锚点 | ①② | 再 1.24×（合计 2.05×） |
| ⑤ | 上游 PR #91 只读接口 | 无 | 那 9.5% |

## 五、不要做（会砍可见内容）

**「客户端本地推演 + 服务端只发事件」**（把 `m.public` 全量也去掉）会**看得见地**砍掉：
队友棋盘/羁绊的**保真度**（事件化后靠本地回放，任何 RNG / 时序分叉就显示成错的）、**敌人预览**（服务端 RNG
客户端复现不出）；而**结算结果必须留在服务端**（否则可伪造胜负）。所以能砍的是保真度与预览，**砍不掉权威层**。
